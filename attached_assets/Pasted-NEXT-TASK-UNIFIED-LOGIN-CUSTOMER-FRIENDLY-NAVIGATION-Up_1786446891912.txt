NEXT TASK — UNIFIED LOGIN & CUSTOMER-FRIENDLY NAVIGATION

Update the existing authentication experience so the website feels like a professional e-commerce store such as Jumia.

IMPORTANT:
- Do not redesign the entire website.
- Do not remove existing authentication logic.
- Do not create duplicate authentication systems.
- Keep React + TypeScript + Express + Prisma + Neon.
- Keep ADMIN and CUSTOMER roles properly separated.
- Do not implement password-change functionality yet.

1. NAVIGATION

Change the public navigation link currently labelled:

"Admin"

or

"Admin Portal"

to:

"Login"

Customers should never see an "Admin Portal" link in the public website.

The Login link should be a normal customer-facing authentication entry point.

2. UNIFIED LOGIN PAGE

Use:

/login

The login page must allow BOTH:

- Customers
- Administrators

to log in.

Do not create separate public login pages for admin and customer.

Login form:

- Email
- Password
- Login button
- Signup link

Example:

Don't have an account? Sign up

3. LOGIN LOGIC

When a user submits email/password:

Backend authenticates the credentials.

Then determine the user's role.

CUSTOMER:
→ authenticate
→ redirect to the normal shopping experience/homepage

ADMIN:
→ authenticate
→ redirect to /admin

Do NOT determine the role from frontend input.

The backend/database must be the source of truth.

Do not allow the user to select:

"I am an admin"

or:

"I am a customer"

4. CUSTOMER SIGNUP

The Login page must contain a clear:

"Create account"

or

"Sign up"

link.

Signup should create a CUSTOMER account by default.

There must be NO public option to register as ADMIN.

Customer signup should continue using the existing customer authentication implementation.

5. ADMIN ACCOUNT

The initial administrator must NOT be created through public signup.

Use the existing secure initial-admin mechanism.

The initial admin credentials should be configurable through server-side environment variables/secrets.

For example:

ADMIN_EMAIL
ADMIN_PASSWORD

Do NOT hardcode the real admin credentials in source code.

Do NOT expose these values to the frontend.

The Replit Secrets/environment configuration should be used for the initial admin setup.

6. INITIAL ADMIN CREATION

Review the existing admin authentication implementation.

If an initial admin seed/setup mechanism already exists, improve it rather than creating another one.

The mechanism should:

- Read ADMIN_EMAIL from environment variables.
- Read ADMIN_PASSWORD from environment variables.
- Hash the password securely.
- Create the admin account if it does not already exist.
- Never store the plaintext password in the database.

If the admin already exists, do not accidentally create duplicate admin accounts.

7. ADMIN ROLE

The database remains the source of truth.

Example:

User:
email = customer@example.com
role = CUSTOMER

→ Customer experience

User:
email = configured admin email
role = ADMIN

→ Admin Portal

Do NOT determine admin status simply by checking whether the email matches ADMIN_EMAIL during every login.

The user's stored role must be authoritative after the initial admin account is created.

8. ADMIN ACCESS

After an ADMIN successfully logs in:

→ /admin

After a CUSTOMER successfully logs in:

→ homepage or previous customer destination

If a CUSTOMER manually visits:

/admin

the existing authorization middleware must reject access.

Do not rely on frontend route protection alone.

9. LOGIN REDIRECT

Preserve the page the customer was originally trying to access where appropriate.

Example:

Customer clicks Add to Cart
→ Login
→ Successful login
→ Return to shopping/cart flow

Do not always force customers to the homepage if a more useful destination is available.

10. AUTHENTICATION STATE

Review the existing authentication context/hook.

There should be one reliable source for:

- authenticated state
- current user
- user role
- loading state
- logout

Avoid duplicating authentication logic throughout components.

11. HEADER AFTER LOGIN

When a customer is logged in, the public navigation should feel like an e-commerce website.

Instead of showing:

Login

show an appropriate customer account indicator such as:

Account
or
Customer name

Keep this simple.

Do NOT create a customer dashboard/portal yet.

The account area can later contain:

- Orders
- Profile
- Logout

12. ADMIN NAVIGATION

Inside the Admin Portal, continue using the existing admin navigation.

The public website should never expose admin-specific navigation.

13. SECURITY

Ensure:

- CUSTOMER cannot access admin endpoints.
- CUSTOMER cannot access /admin.
- ADMIN can access admin endpoints.
- ADMIN can still use normal authenticated functionality where appropriate.
- Role comes from the authenticated backend user.
- Passwords are hashed.
- Admin secrets remain server-side.
- ADMIN_PASSWORD is never returned by an API.
- Authentication cookies/tokens remain secure.

Do not weaken the existing admin authentication middleware.

14. PASSWORD CHANGE

DO NOT implement admin password change yet.

However, structure the authentication system so that:

Admin password change

can be added later without restructuring authentication.

The current initial admin credentials should be changeable through the secret/environment configuration during setup, but do not confuse this with a user-facing password-change feature.

15. GOOGLE LOGIN

If Google OAuth is already configured, keep it compatible with the unified authentication system.

If it is NOT configured:

- Do not fake it.
- Do not invent credentials.
- Leave it as a future authentication option.

16. TEST

Test:

2. Customer can sign up.
3. Customer can log in.
4. Customer is redirected to the normal store.
5. Admin can log in using the configured admin credentials.
6. Admin is redirected to /admin.
7. Customer cannot access /admin.
8. Customer cannot call admin APIs.
9. Admin navigation remains functional.
10. Public navigation shows "Login", not "Admin".
11. Logged-in customer sees an account indicator.
12. Logout works.
13. Invalid credentials are rejected.
14. Admin password is never exposed.
15. No duplicate admin is created.
16. Production build succeeds.
17. TypeScript checks succeed.

Verify compatibility with:

Frontend → Vercel
Backend → Render

ADMIN_EMAIL
ADMIN_PASSWORD
AUTH_SECRET
DATABASE_URL

Do not commit secrets to Git.

1. Unified authentication flow.
